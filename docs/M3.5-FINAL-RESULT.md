## The failure and its evidence limit

The second gate completed the route round trip and its second exact restoration
of the original legacy route. During final cleanup it needed to return to the
live preview found at entry. Ordered child receipts and the runner source locate
the exception at the **`cloudflare.py status` read following a successful
`reverse` command inside cleanup's `op("routeReverse")`**. That read exited 2
after 4,570 ms; cleanup never reached its following `routeCutover` call.

The gate records `owned Cloudflare route: restore failed: python3
scripts/beta/cloudflare.py failed (exit 2)`. Its 61 recorded assertions are true,
but this cleanup exception correctly makes the overall result **failed**. There
is no passing `M35-PLACE-01-entry-restored` assertion in run 2. The journal at the
stop was `reversed`, with no pending mutation. Independent provider readback
confirmed exact original routing and absence of the two preview sibling records.

**The underlying reason for the status read failure is unknown.** The harness
retained exit status and duration but discarded the Python refusal text and
provider verb. The receipt cannot distinguish a transport/API failure from a
state, ownership, lock or input refusal. A later successful read is not proof
of what failed earlier. No claim of a confirmed Cloudflare outage or confirmed
metadata bug is supported.

A future assignment should retain an allowlisted provider verb/refusal code and
assess bounded read-only reconciliation without blind mutation retries or weaker
ownership checks. That implementation was not performed after this failed gate.
