# M3.5 restricted preview scenario and failure inventory

## Recovery evidence inventory (2026-09-25, before implementation)

Follow [the recovery plan](M3.5-RECOVERY-PLAN.md). At the real browser/HTTP
save boundary, retain a safe action/request/response timeline and editor state
before cleanup. An absent or disabled button must fail with that state; an
input that did not reach the intended value must fail before claiming a write.
No request, network timeout, authentication rejection, validation rejection and
stale revision must have distinct observed outcomes. A successful response
without the exact durable revision fails API/PostgreSQL readback; a durable
write without UI acknowledgment fails the UI step without losing the write
evidence. A conflict must preserve typed values and cannot silently resubmit.
Cleanup failures retain exact owned identities and fail the run separately.

Prove this evidence with a deliberately rejected synthetic browser save that
leaves the latest durable revision unchanged. No unit tests are needed. Each
focused phase uses the existing E2E actions/oracles, explicit prerequisites,
incremental evidence and exact cleanup; skipped phases cannot count as full
acceptance. Exercise the remaining dependencies, including route reapplication,
before two clean full gates. Every full-gate failure still stops the loop.

Read-only recovery review identified additional failure paths before edits:
an accepted long run ID can exceed the publication slug limit, so derive a
bounded unique slug without weakening publication validation. If a database
stop command changes state then fails, the startup drill must still restart
that exact database in its cleanup. If a restored-app checker cleanup fails,
retain its exact owner identity and count it as remaining; restore-database
cleanup alone is insufficient. Record cleanup of tracked restore targets even
when the restore operation throws before returning its IDs. Validate these
at the real focused restore/startup boundaries, including bounded injected
failure after owned resource creation, rather than adding unit tests.

The first focused save capture observed HTTP 400 `malformed_if_match`.
Independent readback found the latest preview's ETag stays `"1"` at the
control API and local edge, but becomes `W/"1"` on public compressed responses.
Before correcting the preview response headers, define these E2E oracles:
public identity/gzip/browser encodings retain the strong revision validator;
a valid browser save writes the exact next revision and survives reload;
an invalid introduction returns validation rejection without a write; and a
genuinely stale revision still cannot overwrite the latest draft. Preserve the
strict If-Match parser; do not normalize weak tags or silently resubmit edits.

**M35-STATIC-01 delivery-policy failure (September 25 focused run).** The
`middleware-static-20260925-b` browser loaded the approved home, detail and
CSS with HTTP 200 while dashboard, control, demo gateway, runtime and provider
were stopped, but both pages requested a Cloudflare Web Analytics beacon from
`static.cloudflareinsights.com`. The no-dependent-request oracle therefore
failed; this is an external dependency added to the delivered HTML, not a
publisher asset. Apply `Cache-Control: private, no-store, no-transform` only
to the restricted portfolio proxy response and repeat the same fresh-browser
outage check. Keep the no-external-request assertion exact, confirm approved
content and CSS remain available, and verify anonymous access remains denied.
Cloudflare [documents](https://developers.cloudflare.com/web-analytics/get-started/)
that `public, no-transform` prevents automatic beacon injection on proxied
pages. Applying `no-transform` with `private, no-store` follows this preview's
access boundary and requires verification at the public browser boundary; the
header alone does not establish the fix.

**M35-PLACE protected HTML readiness failure inventory (2026-09-25).** The
`middleware-route-20260925` focused run completed the reapply stability window
with all anonymous root and malformed dashboard API probes passing, then its
one-shot approved portfolio HTML request returned HTTP 530 / Cloudflare 1033.
Those probes did not test authenticated HTML delivery. Keep the same
300-second deadline and 20-second shared stability window, and also require
HTTP 200 HTML responses from protected dashboard root, demo root and the exact
currently published portfolio path. Read that path from the owner's

resets the whole window. Retain only safe status/MIME and Cloudflare cache,
Ray, 1033 or transport diagnostics. The final approved-content assertion stays

**M35-RECOVER initial browser-load diagnostic inventory (2026-09-25).** The
`middleware-restore-20260925` focused run passed the public API and release
checks, then timed out waiting for Chromium's initial dashboard auth form,
before any restore operation. Its receipt retained no initial document or
asset response timeline or bounded page-state snapshot, so the cause remains
unconfirmed. Before one focused reproduction, retain only allowlisted browser

## HOST-248 failed-gate diagnostic correction (2026-09-24)

The primary's private public-route diagnostic
`/var/lib/hostlet-preview/private/diagnostics/public-route-20260924-c/observations.json`
observed valid TLS and the expected Cloudflare records and healthy tunnel for
all three hosts. Requests moved from HTTP 530/Cloudflare 1033 to 401, briefly
reverted at 20:38:16 UTC, and all curl and Node probes returned 401 at 20:38:31
UTC, about 77 seconds after the first observation, without an application or
configuration change. Cloudflare's [proxy-status documentation](https://developers.cloudflare.com/dns/proxy-status/)
states that proxied records use a 300-second TTL and locally observed changes
can take longer. This supports a single bounded 300-second public-route
propagation deadline after cutover, with concurrent probes of all three hosts
and a 20-second continuous all-401 stability window. Any non-401 response or
transport error resets that window. Record each probe and its safe Cloudflare
Ray identifier and 1033 code when present, without retaining response bodies.
An unready route still fails, reverses exactly and stops the full gate; feature
assertions and the two-clean-run policy do not change.

The retained `m35-1982519-gate-1` receipt exposed a harness failure at the
real public HTTPS boundary. On each bounded readiness attempt, record the
host, timestamp, elapsed time and either the safe HTTP status or DNS/TLS/
transport error name, code and cause. Flush progress before a failed readiness
check throws, so route reversal and artifact finalization cannot erase the
attempt history. An HTTP response other than 401 remains a failed access
oracle. A failed or interrupted run must still retain exact pre-existing
owner/project/release/publication identities from the private preview manifest
for cleanup, even when the browser journey never starts. The private artifact
must retain its valid rerun command; scan and scrub passwords and tokens, but
do not classify the non-secret Basic username as a credential. Verify this at
the deployed HTTP and failed-artifact finalization boundary; no isolated unit
check is justified.

## Failure inventory and coverage

**M35-EDIT/RECOVER tenant schema readback.** The first focused demo write
reached HTTP 201, but its independent postgres-role query used an unqualified
table name. Provisioning places application tables in `app` and assigns that
search path only to tenant roles. Independent readback must query
`app.journal_items`; restored project checkers must receive grants and search
path for that same schema. Platform restore checks continue to use public.
Verify the same browser-created item through API and SQL, and exercise real
restored application read/write with the actual tenant schema. No schema or
existing database changes are authorized by this harness correction.

**M35-START static virtual host.** A read-only boundary comparison returned
404 with Node fetch and 200 with Node http.get for the same local static page:
fetch did not transmit the configured Host override. The startup outage probe
must send the actual required virtual host using an HTTP client that preserves
it, enforce a finite timeout, consume the response and assert HTTP 200. Verify
this during the real publisher-worker outage; do not accept a wrong-host 404.

**M35-APPROVAL retained UI state.** An existing approval or published job is
already visible before a new action. Element presence must not count as the
new action completing. The first focused approval read the prior revision
before the new request completed; independent SQL then confirmed approval of
the correct revision. Capture each browser POST status and wait for the exact
approved revision and requested publication slug before reading authoritative
pointers. Keep finite deadlines and exact pointer assertions; do not replace
them with an arbitrary delay or accept any existing approved/published state.
The account already owns one fixed site slug (`claim_site` rejects renaming).
Reuse its authoritative current slug, with a bounded generated slug only for
a genuinely unclaimed site. Match the new publication ID as well as its state;
the old job can share the same slug. Never change the product's slug contract
or delete the existing site to make the runner pass.

**M35-STATIC relative links.** Published cards use `href="projects/..."`.
The first focused static check loaded the independent home page but searched
only attributes containing `/projects/`, missing that valid relative link.
Resolve actual browser anchor URLs and require the configured portfolio's
project-detail prefix, then navigate and verify the page/CSS responses during
the outage. Do not alter published links or weaken the origin/path boundary.

**M35-EDIT-01 final response policy (September 25 continuation).** An outer
readiness layer can overwrite the preview's no-transform policy after its
handler has finished. Before installation, run the candidate control process
against the owned populated store on separate loopback ports and request the
real latest-draft endpoint. Its final response must retain private, no-store
and no-transform with a strong numeric ETag. An unrelated account response
must still prohibit caching; unauthenticated preview access must remain denied.
After installation, confirm the same response through the local edge and public
edge using identity, gzip and browser encodings before browser save validation.
Real invalid, stale and successful browser saves must retain their existing
422, 412 and durable-success behavior respectively. Do not loosen If-Match
parsing. This is HTTP/process and browser E2E, not an isolated unit test.

**M35-DB-CLOCK-01 (real-clock provision).** With the preview control using its
normal wall clock (`generation=0`), enqueue one owned project PostgreSQL
provision and run the real database worker once. The scheduler tick may have a
later timestamp than the preceding clock read; the worker must accept that
normal advancement, claim and complete the exact provision operation, and the
owner API must report `ready` with the same database generation and container
identity. An invalid clock schema, a pinned (`generation>0`) tick with a
different time, or a worker/control failure must remain visible and must not
report readiness. Repeat after managed restart to verify retained identity.
This is covered at the M35-COMPOSE/START E2E boundary; no isolated unit test is
needed. A scheduler-only success event or a precreated container is insufficient.

**M35-RECOVER-01 staged application permissions (September 25 continuation).**
The focused isolated restore reached the real restored application probe but
reported `restore_application_probe_failed`. Its selected staged application
rootfs, `dist` and `node_modules` directories are owned by UID/GID 1000:1000
with mode 0700. The checker runs as UID/GID 0:0 with all capabilities dropped,
so it cannot traverse those directories. Derive and validate the non-root
numeric owner of the exact staged rootfs and run the checker as that identity,
while keeping its existing network, read-only filesystem, dropped capabilities
and resource limits. Verify the inspected container user and perform real HTTP
read/write against the populated isolated project restore. Retain exact checker
and restore cleanup on failure; a successful backup or injected-failure cleanup
does not prove the restored application works.

The table above is the E2E inventory required by [TESTING.md](../TESTING.md).
Malformed host, path, session and bootstrap inputs, plus wrong-owner requests,
are covered by M35-PLACE/ACCESS/SEED. Duplicate bootstrap, approval, publish,
restart and route actions, including concurrent/stale completions, must preserve
one durable pointer and the owner's edits in M35-SEED/APPROVAL/START. Timeouts,
cancellation and backpressure become bounded failure receipts in M35-START; no
sleep or generic HTTP 200 is an oracle. M35-EDIT/RECOVER cover transactions,
populated backup/isolated restore and persistence through restart; upgrade
checks apply only to a qualifying populated-state change.
M35-CLEAN covers partial failure and leaks. If a deterministic internal property
proves impossible to observe at these real boundaries, record the exact gap and
write a failing isolated check before its implementation under TESTING.md's
narrow exception; this inventory grants no retroactive unit-test exception.

## Reused M3 evidence

M3.5 does not change release promotion policy or application rollback eligibility.
The two accepted [M3 gate receipts](M3-HANDOFF.md) remain evidence for failed
candidate retention and eligible runtime rollback against current data. Repeating
those unchanged scenarios would require additional builds and runtime capability
measurements unrelated to preview deployment. This scope clarification precedes
any M3.5 full gate; it does not waive a failed test. M3.5 directly exercises the
new managed restart, real populated backup/isolated restore, independent static
serving, access boundary and exact preview route reversal. A later change to
release policy would require its relevant E2E regression coverage.
