## Checkpoint 1 — Make failures observable

Before edits, extend the existing scenario inventory with these failures and
their observed outcomes: absent/disabled save button; changed value absent from
React state; no request sent; network timeout; authentication rejection;
validation rejection; stale revision; success response without durable write;
write succeeds but the UI fails to acknowledge it; and failure during cleanup.

Add narrowly scoped instrumentation to the existing browser/runner helpers:

- Record phase start, action, deadline, result and failure before cleanup.
  Flush after each phase and on thrown errors, rather than only after the
  complete journey. Distinguish a failed assertion, exception and an unreached
  scenario in the report.
- Observe the actual save request by method/path, response status, safe error
  code and validation field paths, timing, expected/returned revision and
  whether a request occurred. Use an allowlist; never retain authentication
  headers, cookies, login bodies, tokens or unrestricted response bodies.
- Record relevant editor state: field matches the intended synthetic value,
  button enabled/busy, notice/conflict text, and current revision. On failure,
  capture a sanitized editor snapshot and, when useful, a screenshot after
  masking authentication inputs. Preserve the failure evidence before closing
  Chromium. An editor screenshot is not an assertion by itself.
- Click only after the control is enabled. A wait must finish on success,
  explicit error/conflict, or its finite deadline. It must not hide a server
  rejection behind a generic success-message timeout.
- For child operations, retain operation name, exit status, elapsed time and
  safe diagnostic fields. Register temporary resource identities as soon as
  they are created so exceptions still leave exact cleanup targets.

Verify the evidence mechanism with one deliberately rejected synthetic save
at the real browser/HTTP boundary. It must fail clearly, leave the original
draft intact, retain a usable private artifact and finish owned cleanup. This
is an expected negative E2E case, not a unit test or an acceptance pass.

**Exit:** primary verifies the failure artifact, secret scan, checksums and
unchanged original draft. Do not proceed with a capture mechanism that still
loses the response or editor state.

## Checkpoint 2 — Diagnose and fix saving

Run one focused reproduction of the actual failing browser action on the
retained preview, with the instrumentation above. Use the deployed application
and protected edge path; a successful direct API call is not a substitute.
Read the current draft/revision first, change one synthetic introduction and
click Save. Record the browser request and UI result, then independently read
the owner API and PostgreSQL.

Classify the result before changing behavior:

| Evidence | Correction scope |
| --- | --- |
| No request, disabled control or input state mismatch | Browser interaction or UI readiness, according to the captured state. |
| HTTP rejection | The exact authentication, validation or concurrency contract named by the response; do not guess from the timeout. |
| Success but missing durable revision | API/storage behavior, with the precise request and database readback. |
| Durable revision exists but success is not observed | UI response handling or the runner's observation. |

Make the smallest correction justified by that evidence. Preserve revision
preconditions and owner edits: do not silently fetch a new ETag and resubmit,
skip validation, accept any status as success, or lengthen a timeout without
evidence that the operation is still making progress.

**Exit:** a focused browser save produces the expected successful response,
the same new revision and exact value appear in API/PostgreSQL, and a fresh
page load retains the value. A second distinct edit from the freshly loaded
revision also succeeds. The rejected-save case still preserves data. Record
the cause, fix, source and private receipt. If the cause remains unknown or
the same failure survives the correction, stop this checkpoint with a report;
do not enter acceptance or cycle through speculative patches.

## Checkpoint 4 — Freeze and run acceptance

The primary may start the first full run only after all of these are true:

1. The save failure is explained and resolved; every remaining phase above
   passed. Changed behavior has current focused evidence and negative cases.
2. Worker diffs are reviewed; `make check` and required builds pass. One clean
   candidate commit includes the final product and harness. Its immutable
   installed source, binary hashes and restricted web build match the candidate.
3. Data and route inventories are current, backups are verified for the scoped
   deployment, retained rollback binaries remain compatible, and all required
   services are ready. Schema checks use actual before/after evidence; no
   reset or restore is an upgrade method.
4. The run can start from existing edited state and a fresh browser. Unique
   run IDs avoid collisions, partial-seed fixtures are repeatable, and cleanup
   tracks current publication/restore identities even on mid-phase failure.

Run the complete M3.5 gate once. **Any failure: retain the full report, restore
the exact route, finish owned cleanup, block HOST-248 and stop the repair/retry
loop.** Do not run a second gate or apply another fix in that assignment.

If the first run passes, verify its external receipt and run a second complete
gate on the same clean commit and unchanged configuration/fixtures. Both runs
must exercise all required scenarios with fresh browser sessions and preserve
the existing populated stores. A second-run failure also stops the loop; one
pass does not satisfy acceptance. Do not combine partial passes across runs.
